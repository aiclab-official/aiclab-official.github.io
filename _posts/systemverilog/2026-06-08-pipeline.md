# Pipeline vs. No Pipeline for Computation

A pipeline is one of the simplest ways to make a computation engine faster. The basic idea is to split a long piece of work into smaller stages, insert registers between them, and let several inputs move through the machine at the same time.

This is important because most algorithms are limited by how much work must fit into one clock cycle. Without pipelining, a long chain of arithmetic and logic becomes a long critical path. With pipelining, the same work is distributed across stages, so the design can usually run at a higher clock frequency and maintain higher throughput, although at the cost of increased latency.


For example, consider a multiply-accumulate block, a FIR filter, a matrix inner-product, or a floating-point arithmetic unit. In all of those cases, the question is the same:

- Should I do everything in one cycle and keep the design simple?
- Or should I split the algorithm into stages and get better throughput?

The tradeoff is straightforward:

- **No pipeline**: lower design complexity, but one long combinational path and a lower maximum clock.
- **Multi-stage pipeline**: more registers and control logic, but a shorter critical path and higher throughput.

The key point is that pipelining usually improves throughput, not latency. A single item may still take several cycles to pass through the machine, but once the pipeline is full, you can often accept one new item every cycle.

## Why pipelining helps computation

Consider a simple compute kernel:

$$y = (a \times b) + (c \times d) + e$$

**No pipeline**

In a single-stage design, all of this may happen in one cycle:

- multiply `a * b`
- multiply `c * d`
- add the products
- add `e`
- optionally normalize, round, clamp, or format the result

That means the clock period must be long enough for every one of those operations to complete. If the path is too long, the design will fail timing (Setup time violations and negative setup slack) or need a much slower clock.

**With a pipeline**

Now split the work into stages:

- **Stage 1**: capture inputs
- **Stage 2**: perform multiplication and alignment
- **Stage 3**: finish addition, rounding, and output formatting

Each stage does less work, so the clock period can be shorter. The total latency may increase by a few cycles, but the machine can process new inputs continuously after the pipeline fills.

That is the real reason pipelines exist in hardware compute engines.

## Handling Memory Contention Accelerators

Consider another practical example:

An accelerator continuously reads data from *Memory A*, performs computations that take several clock cycles, and writes the data into *Memory B*.

While the accelerator is reading data from *Memory A*, CPU A also accesses *Memory A*. Since CPU A has higher priority, the accelerator must wait.

Similarly, when the accelerator attempts to write data into *Memory B*, CPU B requests data from *Memory B*. Because CPU B also has higher priority, the accelerator cannot write into *Memory B*; it must stall its computation and halt reading new data from *Memory A*.

# Pipeline Structure and Control Signals

The pipeline has 4 important signals:
- **input_valid**: indicates that the current stage has valid data to process.
- **input_ready**: indicates that the current stage can accept new data.
- **output_valid**: indicates that the current stage has valid data to output.
- **output_ready**: indicates that the next stage can accept new data.


<figure>
  <img src="/assets/images/22- pipeline-4-signals.svg" alt="Pipeline 4 signals">
  <figcaption>Figure 2: Pipeline 4 signals</figcaption>
</figure>

**input_ready**:
- When the current stage (or active processing unit) does **not** have valid data to output, **output_valid** is low.
- When the next stage (or downstream output) is ready to accept new data, **output_ready** is high.
- When the current stage does **not** have valid data to output **OR** the next stage is ready to accept new data, the current stage can accept new data, so **input_ready** is high.

So, we can express **input_ready** as:

```verilog
input_ready = !output_valid || output_ready
```

Or use the following gates to implement the logic:

**register_en** and **output_valid**:
- When **input_ready** and **input_valid** are high, the current stage can capture new data and start processing it. So the current pipeline register is enabled (**register_en** is high) and in the next clock cycle, **output_valid** will be high, indicating that the current stage has valid data to output.

For example, the first stage captures the inputs, the second stage performs the multiplications, and the third stage completes the additions and produces the final output. When the final output_ready signal is low and the output_valid signal is high, the input_ready signal will be low, which means the final pipeline will stop accepting new data.
This ready signal propagates backward through the pipeline, causing each stage to stall until the downstream consumer is ready to accept new data.
This allows the pipeline to automatically handle backpressure and ensure that data flows smoothly through the stages.

# Issue: Long combinational path
In this pipeline design, the ready signal is generated by combinational logic that checks the output_valid and output_ready signals. If the number of stages is large, the combinational logic can become the critical path of the design, which may limit the maximum clock frequency. One solution to this issue is to register the ready signal every few stages (4 to 8 stages) to break the long combinational path and improve the timing performance of the pipeline.


## Conclusion

Pipelining is a general way to restructure computation so that the expensive part of the work is divided into smaller stages. For algorithmic processing, the win is usually higher throughput and a shorter critical path.
The cost is usually increased latency and more complex control logic.
